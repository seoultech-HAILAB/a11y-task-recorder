## 확인한 것

- Python 110개(2개 건너뜀), node 34개 통과.
- 헤드리스 Chromium 흐름 점검(확장 응답과 NVDA 연결은 합성): 번호 입력, 없는 번호 오류, 연습 자동 시작, Tab/Shift+Tab 각 9번에도 초점이 사이트 안, 과업으로 돌아가기 뒤 페이지 상태 유지, 연습 결과의 단축키 사용 안내, 지시문이 시나리오 문장과 같음, 저장 뒤 바로 다음 지시문, 과업 2 앞에서 연습 다시 하기, 새로 고침 뒤 연습이 다시 열리지 않음.

## 실제 NVDA에서 볼 것

1. 과업 화면이 나올 때 지시문만 읽히는지(앞뒤에 다른 문장이 붙지 않는지).
2. 과업 중 Tab을 계속 눌러도 Chrome 도구 모음이나 기록 화면으로 나가지 않는지. 브라우즈 모드에서 사이트 끝을 지나 아래 화살표를 눌렀을 때 기록 화면 문장이 읽히지 않는지.
3. 저장 뒤 다음 지시문이 바로 읽히는지, 그 사이에 "A11y Task Recorder" 같은 소리가 끼지 않는지.
4. 연습 안내 문단의 길이가 적당한지. 길면 문장 단위로 나눈다.
5. 앱 창(`--app`)에서 확장과 NVDA 애드온이 그대로 동작하는지.

## 0.5.4: 0.5.3 Windows + NVDA 재점검(10/29, go) 뒤 작은 수정

0.5.3 재점검은 go였다. 0.5.0 실패 5개(준비5, 10, 15, 17-1, 19)와 0.5.2의 E 잡음이 모두 풀렸다. F4는 input 26건이 모두 web_content/task, browse_cursor였고 애드온 경고 로그는 0줄이었다. NVDA+Tab도 정상이 됐다(입력 훅 스레드의 IA2 호출이 NVDA 초점 객체까지 흐트러뜨린 것으로 보인다).

관찰 3개에 대한 처리:

- 결과 화면에서 친 키가 세션 input에서 빠졌다(0.5.2 93건, 0.5.3 26건): 의도한 동작이다. 결과 입력 시간은 과업 시간이 아니고(0.4.4부터 서버가 결과 입력 중 이벤트를 받지 않음), 0.5.2에서 들어간 것은 결과 화면에서 잡힌 키가 "과업으로 돌아가기" 뒤에 서버에 도착해 과업 기록으로 들어간 경우로 보인다. 0.5.4는 서버가 돌아가기 전 결과 입력 구간(`task_resume.previous_task_ended_at`부터 돌아간 시각까지)에 잡힌 NVDA·브라우저 이벤트를 받지 않는다.
- 검증 알림("성공인지 실패인지 골라 주세요.")이 남은 채 돌아가면 알림과 사이트 전체가 읽혔다(1/1): 돌아갈 때 알림을 먼저 지운다.
- 17-1의 10초 뒤 다시 열기는 지연이 재현되지 않아 Windows에서 확인하지 못했다. 헤드리스로는 준비 실패 뒤 과업 시작으로 회복하는 경로만 확인했다.

## 0.5.5: 0.5.4 짧은 확인(10/29, go) 뒤 관찰 2개

0.5.4 확인은 go였다. 알림 뒤 돌아가기에서 다시 읽히는 문장이 없었고, 결과 화면 키는 세션에 0건 들어갔으며, input 13건은 모두 web_content/task, browse_cursor였다.

- 돌아가기 위치가 가상 커서가 아니라 시스템 초점이었다(2/2). H, K로 읽어 내려간 참가자는 링크에 초점을 준 적이 없어서 첫 요소로 돌아갔다. 0.5.5는 NVDA+Ctrl+E를 누르는 순간 애드온이 NVDA의 브라우즈 모드 초점 맞추기(`_focusLastFocusableObject`, 브라우즈 모드를 나갈 때 NVDA가 쓰는 것)로 가상 커서 위치의 초점 가능한 요소에 시스템 초점을 준다. 가상 커서가 글 위에 있으면 그 앞의 마지막 초점 가능한 요소다. 포커스 모드에서는 하지 않는다. NVDA 내부 함수라 실패하면 로그에 "browse cursor focus sync failed"를 남기고 그대로 끝낸다.
- 돌아가기 뒤 다시 끝내면 고른 결과와 답이 비어 있었다: 의도가 아니었다. 돌아가기는 결과 칸을 지우지 않는다. 저장하면 다음 과업에서 비워진다.

## 0.5.11: 과업으로 돌아갈 때 사이트 전체 낭독(10/30 0.5.9 재비교)

0.5.10 재비교에서 0.5.9도 "과업으로 돌아가기" 3/5가 사이트 전체로 읽혔다(0.5.3·0.5.5의 첫 돌아가기도 같은 현상). 돌아가기를 누르면 기록 화면이 결과 칸(돌아가기 버튼 포함)을 먼저 숨기고, 그다음 확장이 사이트의 원래 요소로 초점을 옮긴다. 사이트는 기록 화면과 다른 출처라 초점 이동이 메시지를 한 번 거치고, 그 사이 초점이 기록 화면 문서 자체로 떨어졌다. 과업 중 그 문서의 내용은 사이트 하나뿐이라 NVDA가 문서 전체를 한 줄로 읽은 것으로 본다.

- 기록 화면: 돌아가기를 누르면 결과 칸을 바로 숨기지 않고, 사이트가 초점을 받았다고 알려 오면(늦어도 1.5초 뒤) 숨긴다. 그동안 초점은 돌아가기 버튼에 있다가 바로 사이트의 원래 요소로 간다. 연습 과업도 같다. 기록(재개 시각, 쉬는 시간)은 바뀌지 않는다.
- 헤드리스 점검 `scripts/verify_return_focus.cjs`: 사이트를 다른 출처에서 열고 돌아가기를 3번 하며, 초점이 기록 화면 문서에 머문 순간을 1ms마다 센다. 0.5.10은 돌아가기마다 8~9번, 0.5.11은 0번. 같은 출처 연습 경로(`verify_participant_flow.cjs`)에서는 0.5.10도 떨어지지 않아 이 점검을 따로 둔다.
- 실기(10/30, go): 링크 위 돌아가기 3/3 짧음(KO·LO·DA, 끝낸 링크와 "과업으로 돌아왔습니다."만, 0.5.9는 3/5 전체). 돌아가기 버튼·결과 칸이 다시 읽힌 적 9/9 없음, 연습 돌아가기 짧음, 과업 시작 10회 전체 낭독 0, 돌아간 뒤 끝내기·저장 9/9 정상.
- 남은 한계: CJ에서 끝내자마자 돌아가기는 2/2 전체 낭독. CJ는 과업 시작 때도 사이트 안 요소가 아니라 문서에 초점이 있어(NVDA+Tab "CJ그룹 문서") 돌아갈 요소가 없다. 바로 돌아가기의 나머지 4회는 짧았다(DA 1회는 짧게 읽힌 뒤 화살표·H가 잠시 무음, 다시 했을 때 정상).

## 0.5.10: 과업 시작 때 사이트 전체 낭독(10/30 실험 A 사본 재확인)

사본 수정 재확인(A~D 통과)에서 과업 시작 때 "과업 사이트 프레임" 뒤 사이트 전체(머리글부터 꼬리말까지)가 한 번에 읽혔다(3/7, LO-15·LO-11·DA-10). 같은 현상은 0.5.3·0.5.5의 첫 돌아가기, 0.5.7의 KO 시작(3/5)에서도 가끔 있었다. 과업 시작 때 사이트가 나타나면 NVDA가 그 문서를 새로 연 페이지로 보고 "페이지 로드 때 자동 읽기"로 끝까지 읽는 것으로 보인다(사본이 빨라진 뒤 더 잦아짐).

- 애드온: 기록 화면의 "과업 시작" 버튼에서 Enter나 Space를 누르면(NVDA 시작 단축키도) NVDA의 페이지 로드 자동 읽기를 잠시 끄고, 사이트에 초점이 처음 들어간 2초 뒤(늦어도 40초 뒤) 참가자의 원래 설정으로 되돌린다. 과업 중 사이트 안에서 새 페이지를 열 때는 참가자의 설정 그대로다. 원래 꺼 둔 참가자는 그대로 꺼져 있다.
- 실기(10/30): 과업 시작 12/12, 수정판 10/11 전체 낭독 없음(0.5.9에서는 3/7 전체). 처음에는 "과업으로 돌아가기"에도 같은 처리를 했는데 링크 위 돌아가기 1회가 0.5.9보다 길게 읽혀 돌아가기에서는 뺐다. 뒤의 재비교에서 0.5.9도 돌아가기 3/5가 전체로 읽혀, 돌아가기의 전체 낭독은 0.5.10 때문이 아니라 0.5.3부터 있던 한계가 사본이 빨라진 뒤 잦아진 것으로 본다(알려진 한계, 따로 다룸).
- 키트: 판 번호가 같아도 애드온 파일이 다르면 다시 설치한다(진단판과 같은 0.5.10이 "이미 준비됨"으로 넘어갔다).

## 0.5.9: 설치 안내를 화면낭독기로 읽히게(10/29 요청)

참가자에게 키트와 함께 설치 안내 링크를 준다. 기존 설치안내는 키트를 풀어야 읽을 수 있었고, 눈으로 보는 담당자 기준이었다("검은색 서버 창", "위쪽에 NVDA 연결됨이 보이는지").

- `docs/kit-install-guide.html`: 참가자가 NVDA로 읽고 키보드만으로 설치하는 한 페이지. 단계마다 제목(H로 이동), 누를 키, 들리는 말, 안 될 때. 들리는 말은 Windows 실기에서 실제로 읽힌 문장으로 고쳤다(실행 대화상자·열기 콤보상자, Shift+F10 메뉴의 "압축 풀기", Space 뒤 Enter, 보안 경고 창은 Shift+Tab으로 실행, 테스터 번호 입력란). 시각 표현이 다시 들어오면 테스트가 막는다. 키트 안 설치안내와 같은 파일이다. 진행안내는 `_연구진용/`으로 옮겼다(참가자는 기록 화면 안내를 따른다).
- 실기에서 찾은 키트 문제: NVDA를 켠 채 평가시작을 실행하면 바로가기로 다시 켠 NVDA가 다른 설정(환영 창)으로 떴다(2/2). 0.5.9는 같은 판 애드온이 있으면 NVDA를 건드리지 않고, 새로 설치했을 때만 켜져 있던 `nvda.exe`를 다시 실행한다. NVDA는 UIAccess라 일반 권한으로는 Win32_Process의 경로·인수가 비어 있어, 경로는 QueryFullProcessImageName(제한된 조회 권한)으로 읽는다. 재점검 go: 애드온 있음 NVDA 그대로, 애드온 없음 한 번만 다시 시작하고 설정 유지, NVDA 꺼짐 정상.
- 평가시작.bat의 한글 rem 주석 일부를 cmd가 명령으로 실행해 NVDA가 "is not recognized"를 읽었다(chcp 65001). 주석을 모두 ASCII로 바꿨다.
- 서버 창: 최소화로 열고 요청 줄을 찍지 않는다(그 창으로 가면 NVDA가 계속 읽었다). 기록 화면을 닫으면 3분 뒤 저절로 끝난다(재점검 181초, 194초).
- 연습에서 "본 과업으로 가기" 뒤 지시문 앞에 "알 수 없음, 테스터 번호 바꾸기"가 읽혔다. prepare()가 결과 칸을 먼저 숨기고 서버 응답을 기다린 탓이었다. 응답을 먼저 받고 숨기기와 지시문 초점을 한 번에 한다. 헤드리스 흐름 점검은 그 요청을 0.3초 늦춰 이 경우를 재현한다(고치기 전 실패, 고친 뒤 통과).

## 0.5.7: 저장한 과업 다시 하기(10/29 요청)

모든 과업을 저장한 뒤에는 다시 할 방법이 없었다. 저장한 뒤 기술 문제나 방해로 과업을 제대로 못 한 경우를 막아 두면 그 기록이 그대로 분석에 들어간다. 그래서 막지 않고 다시 하게 하되 앞 기록을 지우지 않는다.

- 지시문 화면, 제한 시간 안내 화면, 모든 과업을 마친 화면에 "저장한 과업 다시 하기"(저장한 과업이 하나라도 있을 때). 페이지 안 그룹에서 과업(과업 번호와 지시문 앞부분)과 이유(기술 문제 / 중간에 방해받음 / 결과를 잘못 저장함 / 기타)를 고른다. 초점은 과업 선택에서 시작하고, Escape와 "취소"는 버튼으로 돌아간다. 브라우저 대화상자는 쓰지 않는다.
- "다시 하기"를 누르면 `POST /api/study/<테스터>/redo`가 그 과업의 새 시도를 만들고(`attempt` +1, `retry_of`는 저장한 시도, `redo_reason`), 그 과업의 지시문부터 시작한다. 그 과업을 저장하면 아직 하지 않은 첫 과업으로 이어진다.
- 진행 중(active, answering)인 과업이 있거나 저장하지 않은 과업이면 서버가 거절한다.
- 저장한 시도는 바뀌지 않고, `attempts.csv`와 `study_attempt.analysis`에 `superseded`로 표시된다. 옛 세션에는 `task_redo` 이벤트(이유, 새 세션, 원래 결과)가 남는다. 어느 시도를 분석에 쓸지는 분석에서 정한다(다시 한 시도는 과업을 한 번 본 뒤다).
