## 3. 키트 상태와 재빌드

## 4. 헤드리스 흐름: SNC http 과업과 우리 사본 과업

기록 화면 자체는 `http://127.0.0.1:8765`(키트 `kit_server.py` 기본 바인딩 127.0.0.1)다. http 상위 문서에 http(SNC)·https(우리 사본) 프레임을 넣는 것은 혼합 콘텐츠가 아니며 차단되지 않는다. Chrome의 HTTPS 자동 승격은 최상위 탐색에만 적용되고, 헤드리스 Chromium에서 프레임은 http 그대로 로드됐다(그 호스트의 https는 다른 사이트 "에스앤씨랩 소개"이므로 Windows에서 프레임이 http로 남는지는 §6에서 눈으로 확인).

SNC 사본 응답(curl): 200, 리다이렉트 없음, `X-Frame-Options`·CSP 없음, 프레임 탈출 스크립트 없음. 페이지 안에 YouTube·korea.kr 하위 iframe이 있고 샌드박스 안에서 정상 로드된다.

10/25 키트(HEAD 코드)로 SNC 과업을 준비하면 세 군데가 막았다. 모두 "우리 사본은 https이고 경로가 `/s/<12자리>/...`"라는 0.4.0 규칙을 SNC 사본에도 적용한 것이다.

1. 업로드 설정이 배정표 `upload_url`(우리 서버) 기준이고 SNC 호스트가 아님.
2. 배정 확인 → SNC 페이지가 프레임에 http로 로드, 준비 확인 통과, 지시문에 초점. SNC 호스트로 `/access` 전송 없음(코드는 우리 출처가 아니면 보내지 않음, `study.js autoLogin`).
3. 과업 시작 → 프레임 안 첫 조작 요소(`메뉴 바로가기` 링크)에 초점.
4. 머리글·건너뛰기 링크·바닥글 `inert`, `#study-top` `aria-hidden`(F2 경로).
5. 창 제목이 "한국에너지재단"으로 바뀜(NVDA+T).
6. 프레임 안 Tab 5번, 같은 출처 링크 클릭으로 하위 페이지 이동. 기록된 브라우저 이벤트가 모두 SNC 주소이고 `frame_id`가 붙음(`page_ready`, `dom_mutation`, `navigation`).

8. 다음 과업(두 번째 SNC 과업) 준비 완료.
9. `POST /api/export-package`로 결과 패키지 ZIP 생성(항목 5개).
10. 기록 화면 페이지 오류 0건.

우리 사본(파라타항공) 경로: 운영 서버에 코드 없이 `GET /s/(마운트)/index.html` 401(잠금 유지), `Origin: http://127.0.0.1:8765`로 숨긴 form 로그인 303, 코드 적용 뒤 같은 주소 200(제목 파라타항공), `runtime.js` iframe 가드 0건, `/upload/status` bearer 200, 응답 CSP `frame-ancestors`에 `http://127.0.0.1:8765` 포함. 키트의 파라타 과업 3건은 모두 같은 시작 주소다. 로컬 검증기(`verify_single_window.cjs`)는 수정 전후 모두 24개 통과(숨긴 form 자동 로그인, 코드 입력 없음, 업로드·수정본·제한 시간·코드 없는 키트 오류 표시 등).

## 5. 다이소몰·롯데시네마 경로가 바뀔 때 다시 만들 것

내일 세션은 10/25 배정표 그대로이므로 해당 없음. 이후 Codex 작업으로 운영 카탈로그(`runs/<런>/operator-catalog.private.json`)의 `/s/<id>/...` 경로가 바뀌면:

1. 배정표(비공개 JSON)를 다시 만든다. 정식 경로는 `python3 scripts/build_study_catalog.py --assignments <tester_tasks.csv> --spec <scenario_spec_final.json> --operator-catalog ~/workspace/a11y-user-context-lab/runs/<런>/operator-catalog.private.json --output ~/.local/share/a11y-study-hosting/<이름>.catalog.json`. 작은 배정표는 10/25처럼 손으로 써도 되며, 이때 우리 사본 주소는 자리표시 `https://study-copy.invalid/s/<새 id>/...`로 적는다(빌더가 `--site-origin-file`의 `origin`으로 바꿔 넣음). SNC 과업은 실제 http 주소를 그대로 적는다(SNC 호스트는 비공개 파일에만).
2. 키트를 다시 만든다. 파일 이름 첫 부분(`<이름>`)이 키트 이름 끝에 붙는다.
   ```
   python3 scripts/build_release_kit.py \
     --catalog ~/.local/share/a11y-study-hosting/<이름>.catalog.json \
     --access-code-file ~/.local/share/a11y-study-hosting/access.json \
     --site-origin-file ~/workspace/a11y-user-context-lab/runs/<운영 서비스가 서비스하는 런>/operator-catalog.private.json
   ```
3. 새 마운트가 `--public-mount`(코드 없이 공개)면 기록기는 로그인 화면을 만나지 않아 바로 준비 완료로 가므로 추가 작업이 없다. 잠긴 마운트면 기존대로 숨긴 form 로그인.
4. `dist/SHA256SUMS`에 새 ZIP 해시를 적고 내부 경로로만 전달한다.
5. 기록기 코드(§4)는 다시 바꿀 필요가 없다. CSP의 http 출처는 배정표에서 자동으로 읽는다.

### 8.3 과업 중이나 끝난 뒤 이전 페이지·메인 화면으로 돌아갈 수 없음

원인: 사이트가 기록 화면의 iframe 안에서 돈다. Chrome의 뒤로 가기(Alt+왼쪽 화살표)는 탭 전체 기록을 거슬러 가므로, 과업을 시작한 페이지에서 한 번 더 누르면 이전 과업의 페이지, 사본 로그인 단계, 연습 화면, 기록 화면 자체의 이전 주소로 간다. 헤드리스에서 프레임 안 두 페이지를 이동한 뒤 탭 기록으로 세 번 뒤로 가자, 두 번은 프레임이 정상으로 돌아왔고 세 번째에는 기록 화면이 about:blank로 바뀌어 과업 화면 전체가 사라졌다. Alt+Home은 브라우저 홈페이지로 탭 전체를 바꾼다. 헤드리스에는 브라우저 단축키가 없어 Chrome 자체의 Alt+왼쪽 화살표가 키로 무엇을 했는지는 재현하지 못했다. 사이트 로고·홈 링크가 사본 안에서 어디로 가는지는 사본마다 다르며 사본 쪽(Codex) 확인 대상이다. 또 기존 브라우저 이벤트는 프레임 안 뒤로 가기를 `direction: "new"`로 적는다(Chrome이 하위 프레임 이동에 `forward_back` 표시를 주지 않음). 이번 수정의 `site_navigation` 이벤트로 구분할 수 있다.

수정:
- `browser-extension/content.js`: 기록 화면의 사이트 프레임(`location.ancestorOrigins`가 기록 화면이고 부모가 최상위)에서만 Alt+왼쪽 화살표, Alt+Home(그리고 BrowserBack, BrowserHome 키)의 기본 동작을 막고 기록 화면에 알린다. 다른 사이트와 다른 탭은 그대로다. 기록 화면이 요청하면 프레임 자신의 기록(Navigation API)에서만 뒤로 가며, 과업을 시작한 기록 항목보다 앞으로는 가지 않는다. 과업 시작 때 초점 요청에 시작 항목을 답한다.
- `static/study.js`: 같은 키가 기록 화면 자체나 연습 화면(같은 출처라 확장이 없음)에 떨어져도 같은 동작을 한다. '과업 처음 화면'은 프레임을 과업 시작 주소로 다시 연다. 이동 뒤에는 과업 시작 때처럼 사이트 첫 요소에 초점을 둔다. 시작 페이지에서 뒤로를 누르면 "과업 처음 화면입니다. 더 돌아갈 페이지가 없습니다."를 사이트 아래 상태 영역으로 읽어 준다. 과업 중이 아닐 때(준비, 결과 입력, 완료) 두 키는 아무 일도 하지 않아 기록 화면을 떠나지 않는다.
- `static/index.html`, `static/styles.css`: 사이트 아래 '과업 끝내기' 옆에 '이전 페이지 (Alt, 왼쪽 화살표)', '과업 처음 화면 (Alt, Home)' 버튼. '과업 끝내기'와 같이 Tab 순서에서는 빠지고 마우스와 브라우즈 모드로 닿는다. 과업 중에만 보인다.
- 기록: 대시보드 이벤트 `site_navigation` `{action: back|start, trigger: site_key|recorder_key|button, moved, reason}`. 실제 페이지 이동은 기존 `navigation` 이벤트로도 남는다. 연습은 기록하지 않는다.
- 결과 입력과 끝내기 흐름은 그대로다(결과 입력 중 프레임은 계속 잠김).

헤드리스 확인: 로컬 시험 사이트에서 하위, 더 깊은 페이지로 이동한 뒤 프레임 안 Alt+왼쪽 화살표 세 번에 더 깊은, 하위, 홈 순으로 돌아오고 네 번째는 홈에 머물며 안내를 읽음, 기록 화면 주소는 그대로. Alt+Home, 이전 페이지 버튼, 기록 화면에 초점이 있을 때의 Alt+왼쪽 화살표, 과업 처음 화면 버튼 모두 동작하고 `site_navigation` 7건이 남음. 결과 입력 중 Alt+왼쪽 화살표는 아무 일도 하지 않음. 파라타 사본(로그인 뒤 시작)에서도 뒤로가 시작 페이지에서 멈추고 로그인 단계로 가지 않음(`verify_single_window.cjs`).

Windows 확인:

### 8.4 과업 시작 때 "사이트에 접속할 수 없습니다. 연구진에게 알려 주세요."

`static/study.js`가 이 문장을 내는 경로는 넷이다. (가) 확장 응답이 `ok: false`이고 오류 문장이 없을 때(기록 서버 오류 `collector_error` 말고 모든 실패 사유). 준비 대기는 이런 응답을 20초 동안 다시 묻고 그래도 실패면 이 문장을 낸다. (나) 20초가 지나도 준비 완료가 아닐 때(`loading`, 사본 확인 실패 등). (다) 로그인 화면이 남았을 때. 키트에 코드가 없거나, 코드의 사본 서버 출처가 과업 주소와 다르거나(자동 로그인을 하지 않음), 코드를 보냈는데 다시 로그인 화면이 나올 때. (라) 준비 실패 뒤 4초 주기 재확인에서 여전히 준비가 안 됐을 때. 확장이 15초 안에 아예 답하지 않으면 이 문장이 아니라 "기록 프로그램에 연결할 수 없습니다."가 나온다.

(a) SNC http 사본에서 날 수 있는 경우:
- 기록 화면 CSP `frame-src`에 SNC 출처가 없음(f3c1bb2 이전 키트, 또는 배정표 주소와 실제 주소의 호스트·포트가 다름). 프레임이 차단되어 `net::ERR_BLOCKED_BY_CSP`. 이전에는 "준비 시간 초과"와 구분되지 않았다.
- 확장이 배정 주소를 거부(f3c1bb2 이전, 또는 주소에 쿼리·조각·자격 정보가 있음): `invalid_assignment_url`.
- 프레임 주소가 배정 주소와 글자 그대로 다름: 서버 리다이렉트, 경로 끝 `/` 차이, `;jsessionid=` 붙이기, https 승격. `wrong_url`. SNC 경로가 Java 웹앱 형태(`.do`)이고 http 하위 프레임은 SameSite 기본값(Lax) 때문에 SNC 세션 쿠키를 받지 못할 수 있으므로 Windows에서 확인할 가치가 있다.
- 참가자 PC에서 SNC 서버에 닿지 않음(서버 꺼짐, 방화벽, DNS): 오류 화면, 이전에는 "준비 시간 초과".
- 페이지가 무거워(YouTube 등 하위 프레임) 20초 안에 `readyState`가 `complete`가 되지 않음: `loading`. 이 경우 4초 재확인에서 나중에 준비되면 저절로 지시문으로 넘어간다.
- 확장이 프레임에서 답하지 않음(확장 미설치·재시작): `extension_unavailable`.
- 배정표에 SNC 과업의 준비 단계가 들어 있음: `preparation_scope_mismatch`.

(b) 우리 사본에서 날 수 있는 경우:
- 잠긴 마운트(파라타, 코드 없으면 401): 키트에 코드가 없음, 키트 코드의 출처가 과업 주소 출처와 다름, 오늘 사본을 다시 만들며 접속 코드가 바뀌어 내장 코드가 거부됨(다시 로그인 화면, 또는 `/access` 오류 화면에서 `wrong_url`). 오늘 사실관계(파라타는 401, 다이소몰·롯데시네마는 코드 없이 200)로는 파라타 과업에서 이 경로가 가장 유력하다. 접속 코드 파일과 운영 서버는 열어 보지 않았다.
- 사본 서버의 `frame-ancestors`에 `http://127.0.0.1:8765`가 빠짐(서버를 다른 설정으로 재시작): `net::ERR_BLOCKED_BY_RESPONSE`.
- 재빌드로 마운트 id나 페이지 경로가 바뀌어 배정표 주소가 없어짐: 404 화면에 `capture-source` 메타가 없어 `capture_missing`, 또는 다른 주소로 넘어가 `wrong_url`.
- 공개 마운트(다이소몰·롯데시네마): 로그인은 없으므로 사본 확인만 남는다. 재빌드 사본에 `capture-source` 메타가 없으면 `capture_missing`, 다이소몰 장바구니 준비 요소가 바뀌면 `loading`(단계 `cart_elements`).
- 두 경우 공통: 기록 화면을 `http://127.0.0.1:8765`가 아닌 주소(예: localhost)로 열면 `untrusted_origin`.

수정:
- 원인 분류(`recorder/site_check.py`): 로그인 필요, 주소 허용 안 됨, 준비 시간 초과, 확장 응답 없음 네 가지에 사이트 연결 실패(네트워크 오류), 사본 확인 실패(메타·준비 단계), 기록 서버 오류를 더했다. 코드를 보낸 뒤 `/access`가 오류 화면이면 로그인 필요로 분류한다.
- 확장(`background.js`): 대시보드 탭의 사이트 프레임 로드 오류(`webNavigation.onErrorOccurred`의 `net::` 코드)를 기억했다가, 프레임이 없거나 오류 화면이라 답이 없을 때 `frame_error`와 그 코드를 돌려준다. 사본 안에 끼워진 동영상 프레임의 오류는 섞이지 않는다. 시간 초과 때 어디서 멈췄는지 `stage`(frame, content, page, cart_elements)를 붙인다.
- 기록 화면(`study.js`): 준비가 끝날 때마다 대시보드 이벤트 `site_preparation` `{result, reason, login(no_code|other_origin|submitted), net_error, stage, elapsed_ms, retry}`를 남긴다. 기록 서버가 원인과 이름을 붙여 돌려준다. 참가자 문장은 짧게 원인 이름만 붙인다. 예: "사이트에 접속할 수 없습니다(로그인 필요). 연구진에게 알려 주세요."
- 서버 창: 실패 때 한 줄. 예: `사이트 준비 실패: 테스터 T01 과업 1 · 로그인 필요 (login_required, no_code)`. 주소, 호스트, 코드는 찍지 않는다.
- 결과 패키지: `site_preparation.csv`(시작하지 못한 과업 포함, 테스터·순서·과업·원인·사유·네트워크 오류·걸린 시간)와 `패키지정보.txt`의 "사이트 준비 실패 기록: N건". 시작하지 못한 과업은 완료 세션이 아니라 `sessions/`에 없으므로 이 파일이 유일한 요약이다(전체 기록은 기존대로 `recorder.sqlite3`).

헤드리스 확인: 프레임 거부 사이트(`X-Frame-Options: DENY`)는 "주소 허용 안 됨", `net::ERR_BLOCKED_BY_RESPONSE`. 없는 호스트는 "사이트 연결 실패", `net::ERR_NAME_NOT_RESOLVED`. 코드 없는 키트는 "로그인 필요", `login_required`, `no_code`, 서버 창 한 줄. 정상 준비는 `ready`, `login: submitted`.

Windows 확인:
- 이 문장이 나오면 괄호 안 원인 이름을 그대로 적고, 서버 창의 "사이트 준비 실패:" 줄을 옮겨 적는다.
- 세션이 끝나면 결과 패키지의 `site_preparation.csv`를 연구진에게 보낸다.
- 파라타 과업이 "로그인 필요"이고 서버 창 줄에 `submitted`가 있으면 내장 코드가 거부된 것이다. 현재 접속 코드로 키트를 다시 만들어야 한다. `no_code`면 코드 없이 빌드된 키트다.
- SNC 과업이 "주소 허용 안 됨"이면 서버 창 사유가 `wrong_url`인지 `frame_error`인지 적는다. `wrong_url`이면 실제 프레임 주소(리다이렉트, `;jsessionid=`)를 확인한다.
